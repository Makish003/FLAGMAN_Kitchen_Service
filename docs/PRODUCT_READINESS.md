# Аудит готовности «Флагмана» к эксплуатации

Дата: 10 октября 2026. Проверен проект `D:\Progs\hack`.

Вывод: это работающее и проверенное локально MVP с сильным доменным ядром. До первого эксплуатационного релиза одного ресторана остаются проверка развёртывания, восстановление данных, устранение ограничений полного чтения БД и доведение повседневных сценариев интерфейса. Готовность к публичному деплою пока не подтверждена. Процент готовности не приводится: согласованного объёма production-релиза нет.

## Источники и границы

- Исходный код backend/frontend, Dockerfile, Compose, скрипты запуска, тесты и документация.
- `DEVELOPMENT_PLAN.md` и `TASKS.md`: исходные R01–R25 относятся к локальной приёмке MVP.
- `DESIGN.md` и `STRATEGY.md`: оригинальные экспорты из чата `codex://threads/01a125a3-3c02-7a00-9678-b5cd52f4bc8b`. Локальная запись чата подтверждает экспорт в эту рабочую папку; во время аудита STRATEGY.md ещё создавался, затем стал доступен и был прочитан.
- `docs/VERIFICATION.md` и прежние логи использованы как исторические свидетельства; ниже отдельно перечислены повторённые проверки.
- В папке нет Git-репозитория; Docker CLI не найден. Удалённый хостинг и внешние интеграции не проверялись.

## Пробелы по приоритету

### P0 — надёжность первого развёртывания

1. **Нет доказательства контейнерного запуска.** Compose рассчитан на локальный HTTPS с внутренним сертификатом и привязкой к loopback. Нужен проверенный production-профиль: домен, TLS, готовность API, volume, права непривилегированного пользователя, рестарт и обновление.
2. **Нет воспроизводимого backup/restore.** README объясняет опасность копирования `.db` при WAL, но нет инструмента копирования, процедуры восстановления и проверки сверки партий с движениями. Сохраняемые ключи сессий требуют отдельного решения при восстановлении и откате.
3. **Демо-время хранится в БД и применяется независимо от FLAGMAN_DEMO.** `State.Now` всегда прибавляет `DemoOffsetHours`; выключение демо закрывает API изменения часов, но не сбрасывает уже сохранённый сдвиг. Нужны отказ запуска production с такой базой либо явная безопасная процедура её изоляции. Реальные данные нельзя молча пересчитывать.
4. **Нет автоматической приёмки релиза.** `scripts/test.ps1` запускает доменные тесты и frontend build; E2E требуют отдельного сервера и пустой демо-БД. Нужен один воспроизводимый release-check с изоляцией данных и остановкой своего сервера.
5. **Ошибки API не имеют надёжного контракта.** `api.ts` безусловно разбирает ответ как JSON. Неизвестный API-маршрут может попасть в SPA fallback; ответы proxy/429/обрыв связи могут дать техническую ошибку парсинга. Нужны корректные HTTP-коды, понятные сообщения и correlation ID.
6. **Неопределённый результат операции при потере ответа.** Ключ заказа/поставки живёт только в открытой форме. После закрытия и повторного открытия новый ключ позволяет повторить уже сохранённую операцию. Нужен сценарий восстановления результата по исходному ключу; автоматический повтор с новым ключом недопустим.

### P1 — повседневная работа и рост истории

1. `Store.Load` загружает все таблицы при каждом чтении; `Save` перебирает все записи при каждой записи. Monitor делает это каждую секунду, каждый SSE-клиент тоже читает агрегат раз в секунду. Небольшой snapshot-тест не измеряет эту суммарную нагрузку.
2. `/api/health` также читает весь агрегат. Нет разделения liveness/readiness, метрик ошибок фонового обработчика, размеров истории, задержки списания и актуальности данных клиента.
3. Snapshot отдаёт только 500 партий и 100 записей журналов. Поиск склада локален и не гарантирует нахождение партии вне снимка. Пагинация журналов реализована поверх полного чтения, а не выборочного SQL.
4. События и записи идемпотентности растут без политики хранения. Удаление без правил может сломать replay или защиту повторов; нужен отдельный контракт retention.
5. Навигация живёт в React state: нет устойчивых адресов страниц, восстановления фильтров и обычной работы Back/Forward. Закупки и прогноз объединены с аналитикой, сроки — со складом, хотя стратегия выделяет их как отдельные задачи.
6. Поля дат используют пояс компьютера, отображение — пояс ресторана. Подпись есть, но при работе из другого пояса оператору легко ошибиться. Нужен единый понятный ввод и тест границы срока.
7. Один файл `main.tsx` объединяет страницы, сетевые обновления и формы. Изменение интерфейса становится рискованнее; выделение страниц и общих компонентов должно сопровождать реальную работу над UX.
8. Операционные журналы не заменяют аудит действий: нет личности автора изменения настроек/рецептуры. В рамках одной общей роли можно журналировать действие и сессию, но нельзя достоверно назвать сотрудника.

### P2 — развитие после эксплуатационного пилота

Персональные аккаунты и роли, полноценная инвентаризация и ручные корректировки, цены и денежные потери, импорт/экспорт, несколько ресторанов и внешние интеграции потребуют новых требований и доменной модели. Они не входят автоматически в первый релиз по STRATEGY.md. PostgreSQL также не является обязательным условием: сначала измерить пределы SQLite и убрать полное чтение/сохранение агрегата.

## Соответствие дизайну и стратегии

Сохраняется операционный кабинет на русском для управляющего одного ресторана. Не нужны маркетинговый hero, тарифы, вымышленные отзывы, обещания экономии или переезд на Tailwind/shadcn.

`DESIGN.md` задаёт авторитетные базовые цветовые токены и компонентные состояния. `STRATEGY.md` явно уточняет прикладной вид: sidebar #193f35, primary #245d4c, фон #f6f8f5, текст #23382f, границы #e7ece7, белые карточки; текст 14–16 px, заголовок страницы около 31 px, карточки 18–20 px, кнопки 7 px и панели 10 px. Эти уточнения надо документировать как прикладные токены поверх базы, а не считать два файла полностью идентичными.

Segoe UI/Arial допустим по стратегии; Inter выбран в экспорте. Сам по себе нынешний шрифт не является дефектом. Для согласованного результата предпочтительно локально подключить Inter с поддержкой кириллицы и fallback, сохранив прикладной масштаб стратегии. В текущем SCSS есть многочисленные подписи 8–12 px и разрозненные оттенки: это главные объекты улучшения читаемости и унификации. Наличие dark-токенов в экспорте не делает тёмную тему требованием первого релиза.

## Проверки в этом аудите

- `scripts/test.ps1`: **14/14** критических доменных и SQLite-проверок прошли; production frontend собран.
- Backend Release build с `--no-restore`: **0 ошибок, 0 предупреждений**.
- Измерение существующего теста: snapshot с 1000 партиями в среднем **60 мс**. Это локальная синтетическая проверка, не production-нагрузка.
- Свежий Playwright: **3/3 теста прошли за 21,5 с** на отдельном сервере 15088, уникальной пустой БД `test-results/product-audit-*.db` и случайном тестовом пароле. Использованы временные копии тестов/конфигурации с заменой порта; после проверки они удалены, сервер остановлен. Первый запуск не состоялся из-за занятого 5080; подключение к отдельному порту потребовало разрешённого выхода из sandbox, ограничивающего localhost.
- Свежие `test-results/overview-desktop.png` и `overview-mobile.png` визуально просмотрены: структура кабинета сохранена, mobile не переполняет страницу; мелкие вторичные подписи подтверждают необходимость улучшения читаемости.
- В рамках аудита версии зависимостей и актуальные базы уязвимостей повторно не проверялись; прежний audit из VERIFICATION не является новым заключением.

Практическая граница готовности: сначала проверенный релиз для одного ресторана на одном экземпляре приложения. Распределённую работу и коммерческий SaaS эта приёмка не подтверждает.
