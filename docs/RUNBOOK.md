# Эксплуатация одного ресторана

Контракт: один процесс API, SQLite WAL на локальном постоянном volume, Caddy HTTPS, одна общая роль управляющего. Несколько реплик API и сетевые файловые системы не поддержаны этой приёмкой. Нужны Node 22+, .NET 8 SDK для сборки, ASP.NET Core 8 runtime для артефакта.

Профиль ограниченного пилота: до 1 000 одновременно активных партий при истории из 10 000 партий / 100 000 движений, 10 SSE-клиентах и одном операторе записи. Это локальная синтетическая проверка на i7-9750H/16 GiB, не SLA. Пять конкурентных операторов дают нестабильный p95 записи выше предварительной цели, включая сценарий 1 000 активных партий. Перед ростом повторить `verify-release.ps1 -ActiveBatches 10000 -Operators 5` на целевом оборудовании; отрицательный результат не считать пройденной приёмкой. Конкурентная корректность проверена отдельно и не означает выполнения цели задержки.

Локальная проверка: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/verify-release.ps1`. Создаются случайный пароль, свободные порты и отдельные базы внутри test-results. Пароль не выводится. Рабочий сервер и рабочая БД не используются. Проверка останавливает только свои процессы. Прерывание терминала требует проверить дочерние процессы вручную. `-SkipBrowser` исключает браузер и не означает полной приёмки.

## Конфигурация

| Переменная | Назначение |
|---|---|
| FLAGMAN_PASSWORD | общий пароль не короче 10 символов; хранить в secret/environment |
| FLAGMAN_DB | отдельная база production или demo |
| FLAGMAN_DEMO | true только для демонстрационной базы |
| FLAGMAN_TRUSTED_PROXY | адрес доверенного Caddy, фиксирован в Compose |
| FLAGMAN_SESSION_VERSION | изменить и перезапустить API для отзыва всех сессий |
| FLAGMAN_DOMAIN | DNS-домен production-профиля |
| FLAGMAN_BACKUP_DIR | каталог копий для контроля возраста через ops/status |
| ASPNETCORE_ENVIRONMENT | Production для HTTPS, Development для локального HTTP |
| BASE_URL | адрес выделенного E2E-сервера |
| FLAGMAN_BROWSER / PLAYWRIGHT_BROWSERS_PATH | браузер E2E |

Сессия действует до 8 часов без продления. Смена пароля отзывает старые cookie при следующем запросе после рестарта. Общая роль и sessionId не устанавливают личность сотрудника. После logout pending intent удаляется с устройства; если результат не был получен, до нового ввода проверить журнал. Истёкшая сессия сохраняет intent для восстановления после входа.

## Deploy и обновление

Локальный TLS: `docker compose up --build -d`, https://localhost:8443, доверить CA Caddy. Production: задать секрет и FLAGMAN_DOMAIN, DNS A/AAAA на хост, открыть 80/443, выполнить `docker compose -f compose.production.yaml up --build -d`. API наружу не публикуется. Готовность proxy зависит от healthcheck API. Проверить `docker compose -f compose.production.yaml ps` и логи; процесс API должен быть UID 1654. Новый volume получает права из образа. Для существующего volume заранее проверить владельца 1654 и доступ к /data, не менять права всего хоста.

Перед обновлением сделать проверенную копию, сохранить версию образа/архива и checksum. Схема v2 добавляет SQL-индексы и аудит. Для v1 автоматически сохраняется `.pre-v2-<id>.db` рядом с исходной базой, затем выполняются повторяемые шаги. Неизвестная более новая схема останавливает запуск. Миграцию проводить при остановленном предыдущем API. При ошибке сохранить диагностику и не подменять базу непроверенной копией.

Откат: остановить единственный API, восстановить согласованную пару прежнего приложения и его backup в новый путь/volume. Старый бинарник, не знающий схему v3, не запускать на новой базе. Переключение означает короткий простой; zero-downtime не обещается. Не использовать демо-базу для production; ненулевой сдвиг часов вызывает отказ запуска, сдвиг не сбрасывается.

## Хакатонный кандидат: схема v3 и диск

Схема v3 добавляет optional поля цены партии и календаря в JSON, не переписывая исторические партии. Перед изменением v1/v2 автоматически создаётся .pre-v3-<id>.db; v1 также сохраняет прежнюю pre-v2-копию. Известные старые цены null. Миграцию выполнять при остановленном API. Проверять копию, остатки и движения; не удалять рабочую БД или WAL.

Измеренная задержка SQLite FULL commit зависит от локального диска: на D: были p95 порядка 1.2с и нарушения цели даже одного оператора, на C: три прогона пяти операторов дали p95 заказа 62/66/105мс. Это результаты данного хоста, а не гарантия для произвольного volume. Подтверждать профиль только на выбранном хосте/диске. Прежнее ограничение пилота ниже является историей 1.1.0; актуальные параметры и результаты нового кандидата — HACKATHON_VERIFICATION.

Для изолированной приёмки на нужном диске scripts/verify-release.ps1 и verify-load.ps1 принимают -DataDirectory <новая рабочая папка>. Каждая проверка создаёт внутри отдельную подпапку с уникальным именем, существующие БД не перезаписывает. Не менять synchronous=FULL или транзакции ради цифр. /api/ops/status содержит p95/maximum последних до 2000 samples writerWait/orderPrepareSave/orderCommit/monitorCommit; показатели относятся к текущему процессу и помогают отличить вычисления от хранения.

## Backup и restore

Собрать tools/Flagman.Maintenance. `scripts/backup.ps1 -Database <полный путь> -Directory <защищённая папка>` использует SQLite backup API, затем integrity_check и точную decimal-сверку каждой партии с суммой её движений. Копирование рабочего .db при WAL не использовать. Ежедневный запуск настроить Task Scheduler/cron, с проверкой exit code; по умолчанию сохраняются 7 ежедневных и 4 воскресных копии, параметры Daily/Weekly меняют политику. Копии перенести в защищённое внешнее хранилище; локальный диск не защищает от потери хоста.

`scripts/restore.ps1 -Backup <копия> -NewDatabase <новый путь> -CurrentDatabase <текущая база>` сначала копирует текущее состояние, затем проверяет восстановленную новую БД. Существующие файлы не перезаписываются. Остановить API перед переключением FLAGMAN_DB. Новый путь должен находиться в отдельной папке с новыми Data Protection keys; увеличить FLAGMAN_SESSION_VERSION. Сессии отзываются. Ключи не нужны для чтения БД и сознательно не входят в копию данных. Старые ключи хранить отдельно с доступом только администратора, не включать в release-архив.

## Наблюдение и реакция

Ответственный: администратор выбранного ресторана/хоста; конкретное имя и канал уведомлений назначить перед пилотом. `/api/live` проверяет процесс, `/api/ready` проверяет соединение и схему без загрузки склада. Авторизованный `/api/ops/status` показывает последний monitor tick, ошибку и число SSE. Запросы логируются с requestId, методом, путём, статусом и длительностью; секреты, тела, cookies не логируются. Meter Flagman содержит request.ms, errors, sqlite.busy и доступен .NET diagnostic collector.

Внешний монитор должен уведомлять при readiness failure, monitor tick старше 10 секунд, 5xx, повторном SQLITE_BUSY, диске >85%, отсутствии успешной копии >26 часов. Канал уведомлений подключает администратор хоста. При monitor error проверить журнал по requestId, диск, права и блокировки; перезапустить только после установления причины. API немедленно исключает истёкшие партии из заказов даже при задержке Monitor. При потере связи интерфейс отмечает устаревшие данные и позволяет восстановить прежнюю запись.

Outbox хранит последние ~10 000 событий; каждое SSE-подключение начинает с sync и требует свежий snapshot, поэтому старый cursor безопасен. Requests/idempotency не удаляются: повтор допустим всю жизнь БД; уменьшение срока требует отдельного контракта. История и аудит также не удаляются.

SQLite сохраняет synchronous=FULL и стандартный автоматический checkpoint. Эксперимент с отдельным PASSIVE checkpoint не устранил паузы, поэтому отменён. Длительный читатель может удерживать WAL; следить за размером WAL/диском. Нельзя удалять WAL вручную. Для устойчивой работы нескольких операторов требуется профилирование задержек fsync/очереди на целевом хосте.

## Контейнерная приёмка (обязательна на Docker-хосте)

Build → readiness → HTTPS/login → проверить Secure/HttpOnly/SameSite-cookie и Origin rejection → пустой каталог/рецептура/поставка/заказ → SSE двух клиентов → рестарт → те же остатки → backup во время записей → restore в новый volume → exact movement reconciliation → новые ключи/отзыв сессий → откат согласованной пары. Проверить UID и права нового/существующего volume, stop/restart, мобильную ширину и длинные названия. Записать версии Docker/Caddy/ОС, команды и логи. Без этого production-приёмка заблокирована.

До этой даты запланировать и проверить переход на поддерживаемый LTS. Наличие текущих патчей не продлевает жизненный цикл runtime.
