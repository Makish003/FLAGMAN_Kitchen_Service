# Разделение администратора и менеджера

Роль `admin` имеет полный доступ. Роль `manager` сохраняет операционный кабинет, закупки, приёмку, склад, меню, предложения, аналитику и настройки. Управление аккаунтами и API-ключами, демонстрация и генератор доступны только администратору. Ограничения действуют в интерфейсе и API, включая варианты регистра маршрутов.

Схема v5 однократно переводит прежние аккаунты `manager` в `admin`, сохраняя идентификаторы, логины, пароли и данные. Перед обновлением существующей базы создаётся SQLite backup `*.pre-v5-*.db`. Сессии и старые API-ключи повышенных аккаунтов перестают действовать: необходим повторный вход и перевыпуск ключей. Созданные после миграции менеджеры не повышаются при перезапуске. Последнего активного администратора нельзя отключить или понизить.

Менеджер получает список активных поставщиков через `/api/suppliers` (только ID и имя), поэтому закупки не требуют доступа к аккаунтам. Администратор также может подтверждать приготовление и выдачу заказов сотрудников.

Проверено на изолированных базах:

- Frontend: `npm.cmd --prefix frontend run build`.
- 23 проверки рабочих процессов: `Flagman.Tests.dll --workflows`, включая права аккаунтов, сохранение пароля при миграции и отсутствие повторного повышения менеджеров.
- Playwright: `admin-role.spec.ts`, `roles.spec.ts`, `authorization-paths.spec.ts` — проверки API, навигации, закупок, администраторской обработки заказа, чужих документов и отзыва ключей.

Рабочая база и запущенный рабочий API в рамках этой проверки не перезапускались. Миграция применяется при запуске обновлённого API.
