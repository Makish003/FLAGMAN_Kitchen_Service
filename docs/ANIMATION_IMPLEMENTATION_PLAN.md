# План разработки плавных и быстрых анимаций «Флагман»

Статус: готов к передаче агенту. План описывает будущую реализацию; анимации по нему ещё не внедрены.

## 1. Цель и границы задачи

Сделать интерфейс отзывчивым и визуально последовательным: короткий отклик элементов управления, плавное открытие и закрытие диалогов, мобильной навигации и уведомлений, аккуратное появление содержимого разделов.

Пользователь должен сразу получать результат действия. Движение помогает понять изменение состояния, а не добавляет ожидание. Сохранить бизнес-логику заказов, поставок, восстановления операций, SSE и маршрутизации.

Основная реализация: CSS transitions/keyframes и небольшие React-хуки для жизненного цикла. Новые зависимости по умолчанию не добавлять. Использовать Web Animations API только если конкретный сценарий требует управляемой отмены и CSS получается существенно сложнее; решение описать в отчёте.

## 2. Исходное состояние проекта

Перед началом перепроверить эти сведения в актуальной версии файлов:

Важные особенности:

- Диалоги и toast сейчас размонтируются сразу при обнулении состояния в App. Одного CSS для анимации выхода недостаточно.
- Toast автоматически исчезает через 6500 мс. Сохранить эту длительность и корректно перезапускать её для нового сообщения.
- Desktop toast центрируется через `translateX(-50%)`. Новая анимация не должна перезаписать это позиционирование.
- Мобильная навигация уже управляет inert, прокруткой body, клавиатурным фокусом и Escape. Эти механизмы нужно согласовать с фазой закрытия.
- Snapshot обновляется через SSE и каждые 30 секунд. Обновление данных не должно повторно запускать появление всего экрана.
- App работает в React.StrictMode. Эффекты должны корректно переживать повторный запуск и очистку.

## 3. Визуальная спецификация

Числа ниже — стартовые параметры дизайна. Агент может немного скорректировать их после визуальной проверки, зафиксировав итоговые значения.

| Сценарий | Эффект | Открытие / отклик | Закрытие |
|---|---|---:|---:|
| Кнопка | Цвет фона/текста; для подходящих крупных кнопок сдвиг вниз до 1px при нажатии | 120–140 мс | 120 мс |
| Поле ввода | Цвет рамки/фона; отчётливый focus-visible | 140 мс | 120 мс |
| Combobox | Прозрачность и смещение списка на 4px; поворот стрелки | 140 мс | 100–120 мс |
| Диалог | Прозрачность и смещение на 8px, без масштабирования текста | 200 мс | 140 мс |
| Backdrop диалога | Плавное затемнение, без анимации blur | 180 мс | 140 мс |
| Мобильная навигация | Выезд по X, плавное затемнение подложки | 220 мс | 160 мс |
| Toast | Прозрачность и смещение по Y на 8px | 180 мс | 140 мс |
| Новый раздел | Однократное появление области содержимого: opacity и Y до 4px | 160 мс | Без ожидания ухода предыдущего раздела |
| Изменение статуса | Короткий переход цвета компактного индикатора | 140 мс | — |
| Загрузка | Существующий spinner только пока идёт загрузка | Цикл 1600 мс | Остановка сразу |

Кривые движения:

- Вход: `cubic-bezier(0.16, 1, 0.3, 1)`.
- Выход: `cubic-bezier(0.4, 0, 1, 1)`.
- Микроотклик: `cubic-bezier(0.2, 0, 0, 1)`.

Без пружин, отскоков, постоянной пульсации предупреждений и пересчёта числовых метрик через промежуточные значения. Количества и статусы должны сразу показывать актуальные данные. Hover-эффекты применять при `(hover: hover) and (pointer: fine)`; клавиатурный фокус оформлять независимо от hover.

## 5. Этап B — единые motion-токены и CSS

1. Расширить раздел motion в `theme.json`: длительности micro/enter/exit/navigation, easing enter/exit/standard, расстояния small/medium. Сохранить существующие fast/spin либо явно перевести их потребителей.
2. Для easing и расстояний использовать формат токенов, совместимый с текущим генератором. Не редактировать сгенерированный theme.css вручную.
3. Сгенерировать CSS через `node tools/design/build-tokens.mjs` из корня проекта.
4. Вынести правила движения в понятный раздел styles.scss либо отдельный SCSS-модуль, подключённый до завершающих reduced-motion правил.
5. Указывать конкретные transition-property. Не применять `transition: all`.
6. Основное движение выполнять через transform и opacity. Цветовые переходы оставить на небольших контролах. Не анимировать width, height, top, left, большие тени и blur в основной реализации.
7. Не назначать will-change или translateZ(0) всем элементам. Добавлять временное will-change только при подтверждённой необходимости в профилировании.
8. Разделить позиционирование и движение вложенными оболочками там, где уже используется transform, прежде всего у desktop toast.
9. В reduced motion отключить несущественное движение, сохранив видимость, контраст и текст загрузки.

Приёмка: токены генерируются, сборка проходит, все временные параметры читаются из единого источника, никакие конечные состояния не зависят от animation-fill-mode при отключённых анимациях.

## 6. Этап C — управление присутствием элемента

Разработать небольшой общий механизм присутствия для элементов с выходной анимацией. Возможная структура: `frontend/src/motion/usePresence.ts` и `frontend/src/motion/useReducedMotion.ts`. Названия уточнить по соглашениям проекта.

Контракт:

- Различать желаемое открытие, фактическое присутствие в DOM и фазу: entering/open/exiting/closed.
- Закрытие сначала переключает фазу, затем завершает визуальный выход и размонтирует элемент.
- Повторное открытие во время выхода отменяет устаревшее завершение; старый callback не должен закрыть новый элемент.
- Сохранять содержимое уходящего toast/диалога до конца выхода. Данные формы не очищать раньше времени.
- Реагировать на завершение собственной анимации/перехода, фильтровать события дочерних элементов и нужное animationName/propertyName.
- Иметь ограниченный резервный таймер, связанный с фактической длительностью, на случай отсутствующего события. Не использовать произвольный setTimeout(200) как основной механизм.
- При reduced motion, отсутствии эффекта или изменении настройки во время выхода завершать закрытие без ожидания события.
- Очищать таймеры, слушатели и запланированные кадры при размонтировании. Финальный callback выполняется не более одного раза.
- Не обновлять React state на каждом кадре. Покадровую интерполяцию выполняет браузер.

Приёмка: быстрое open → close → open работает; завершение старого выхода не удаляет новый UI; reduced motion и StrictMode не оставляют зависшие элементы.

## 7. Этап D — диалоги, главный приоритет

1. Согласовать общий жизненный цикл `Dialog`, `OperationModal`, `DetailsDialog` и их присутствие в App. Выбрать единственного владельца открытия/закрытия, избегая двух конкурирующих эффектов.
2. Сохранить нативный `<dialog>` и showModal(). Не заменять их на обычный div ради анимации.
3. Объединить кнопку закрытия и Escape в requestClose. В событии cancel вызывать preventDefault(), чтобы браузер не закрыл dialog до завершения управляемого выхода.
4. При busy сохранить запрет закрытия OperationModal. Повторные нажатия во время выхода не должны отправлять форму или вызывать callback повторно.
5. Пока идёт выход, dialog остаётся в top layer, подложка и модальность сохраняются. После завершения вызвать close() и завершить размонтирование.
6. Вернуть фокус один раз на инициатор; если он удалён/скрыт, выбрать доступную логичную цель. Учесть StrictMode, принудительное размонтирование при выходе из сессии и смену сущности DetailsDialog.
7. Сохранить AbortController загрузки истории и текущую логику busy/result/preview. Анимация не откладывает запрос или получение результата.
8. Для успешной операции передать результат в App сразу: refresh и уведомление не должны ждать визуального ухода. Закрытие формы можно завершать параллельно; при закрытии блокировать повторную отправку.
9. Проверить анимацию ::backdrop на поддерживаемом браузере. Если она требует ненадёжных обходов, оставить статическое затемнение, сохранив анимацию самого dialog; указать это в отчёте.

Приёмка: открытие и закрытие поставки, заказа, продукта, блюда, настроек и истории работают мышью и клавиатурой. Escape внутри Combobox закрывает только список. Принятый заказ отправляется ровно один раз; отклонённый заказ остаётся доступным для чтения.

## 11. Проверки и измеримые критерии

### Автоматические проверки

Добавить `frontend/e2e/motion.spec.ts` либо расширить существующие тесты там, где сценарии уже покрываются. Проверять поведение жизненного цикла, а не копировать CSS в assertions.

- Диалог закрывается после запроса, возвращает фокус и не остаётся в top layer.
- Busy-операция не закрывается и не отправляется повторно.
- Быстрое закрытие/открытие не теряет новый dialog, toast или меню.
- Reduced motion через `page.emulateMedia({reducedMotion:'reduce'})`: все закрытия завершаются, отсутствуют оставшиеся блокировки.
- Переключение reduced motion во время выхода корректно завершает состояние.
- Escape в Combobox не закрывает родительский dialog.
- Resize мобильного меню очищает inert и overflow.
- Успешное сохранение, отклонённый заказ и замена toast сохраняют прежнее поведение.
- SSE при открытой форме не сбрасывает её значения и не запускает появление контейнера заново.
- Проверка axe существующим способом на репрезентативных открытых и закрытых состояниях.

Использовать ожидания по состоянию/DOM/фокусу. Не добавлять фиксированные sleep под длительность CSS. Все изменяющие данные E2E запускать на отдельной demo-БД, как требует существующий набор тестов.

Команды из `frontend` после подготовки окружения:

```powershell
npm run build
npx playwright test e2e/motion.spec.ts
npm run test:e2e
```

Если проверки нельзя выполнить из-за окружения, явно описать причину; не объявлять их пройденными и не снимать ограничения тестов ради зелёного результата.

### Визуальная проверка

- Основные окна: 390×844 и 1440×960. Дополнительно крайние ширины 280/320px и breakpoint 1024px, уже используемые проектом.
- Проверить обычное движение и reduced motion; мышь, touch и клавиатуру.
- Просмотреть видеозапись: нет скачков первой/последней позиции, смазанного текста, мигания backdrop, скачка прокрутки или горизонтального overflow.
- Во время закрытия не появляется краткий доступ к фону модального интерфейса.
- Скрытый opacity:0 элемент не блокирует интерфейс и не остаётся фокусируемым.

### Производительность

- Сравнить trace до/после на одинаковом устройстве, данных и сценариях, отдельно с CPU throttling 4×.
- На обычном окружении ориентир — плавность около 60 FPS, бюджет кадра около 16,7 мс; это цель измерения, а не гарантия для каждого устройства.
- Новые transform/opacity эффекты не должны добавлять повторяющиеся Layout на каждом кадре.
- Не должно быть новых long tasks >50 мс, причиной которых является код управления анимацией. Проверять отдельно от загрузки/отрисовки большого snapshot.
- React Profiler: нет commit на каждом кадре анимации.
- После серии из 20 открытий/закрытий не остаются активные таймеры, слушатели, скрытые модальные элементы или растущий набор слоёв.
- Не требовать идеальные FPS в headless CI: автоматизировать корректность, а плавность подтверждать trace и визуальным просмотром.
