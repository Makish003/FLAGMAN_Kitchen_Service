# Фактическая проверка

Дата: 10 октября 2026. Среда: Windows x64, локальный .NET SDK 8.0.425, Node 24.14.0, Playwright 1.64.0, Chrome for Testing 156.0.8078.4.

## Результаты

- Backend успешно собран: 0 ошибок, 0 предупреждений.
- Production frontend: TypeScript + Vite 6.4.4 + SCSS, успешная сборка; JS ~255 КБ (~77 КБ gzip).
- **14 критических проверок C#/SQLite прошли**, полный вывод в `docs/domain-checks.log`. Реальная файловая БД, не mock. Десять конкурентных соединений: один принятый заказ, девять отказов. Четыре отдельных процесса: один принятый, три отказа. Остатки неотрицательны и равны сумме движений.
- FEFO: 2 кг + 3 кг, расход 2.5 кг — первая партия пуста, во второй 2.5 кг. Заказ с общим ингредиентом отклоняется без расхода. Принятые/отклонённые повторы сохраняют один ID и не дублируют движения/дефициты; конфликт содержимого даёт 409.
- Граница истечения проверена управляемым временем. Повтор обработчика и повторное открытие БД не создают второй потери. Правила от производства/поступления/конца местного дня проверены.
- Рекомендации: срочность растёт при приближении срока, недоступные блюда исключены, совместный план расходует 2000 г рисковой партии ровно один раз.
- Контрольные закупки и аналитика сверены вручную: 500 г расхода отдельно от 500 г потерь. Прогноз при фиксированном спросе даёт границу 72 ч; без истории известное истечение через 4 ч учитывается без выдуманного спроса.
- Генератор с одинаковым seed создаёт одинаковую последовательность 15 входных событий; повтор seed после сдвига времени не применяет их повторно.
- Производительность снимка при 1000 партиях: **59 мс в среднем по 5 чтениям**, локальная машина, тёплый файловый кеш. Цель для демонстрационной нагрузки <2000 мс выполнена. Это не распределённый нагрузочный тест и не обещание производительности большого склада.
- **3 сквозных теста Playwright прошли** в актуальном Chrome, вывод в `docs/browser-checks.log`: все экраны; создание продукта, рецептуры, поставки; принятый/отклонённый заказ; демо-истечение; навигация при ширине 390 px; отсутствие переполнения страницы; API 401/403/409; два SSE-клиента и Last-Event-ID; фоновое списание без заказов; запуск/остановка генератора.
- Desktop 1440 px и mobile 390 px снимки визуально просмотрены: `test-results/overview-desktop.png`, `test-results/overview-mobile.png`. Мобильная таблица скроллится внутри карточки. Переход адаптивной навигации завершён до снимка.
- `npm audit`: 0 известных уязвимостей. `dotnet list package --vulnerable --include-transitive`: известных уязвимых пакетов не найдено. Microsoft.Data.Sqlite 8.0.31 и SQLitePCLRaw.bundle_e_sqlite3 2.1.13. Результат ограничен базами аудита на дату проверки.
- Чистая пустая база автоматически создаётся при запуске; UI загружает демо; журналы и outbox сохраняются на диске.
- Release-сборка опубликована в `output/app` и упакована в `output/flagman-app.zip`. Отдельный запуск опубликованной DLL на 5081 проверил HTML, healthcheck, cookie-вход, создание новой SQLite БД и seed (10 продуктов / 5 блюд); вывод `docs/release-checks.log`. Это framework-dependent сборка: нужен ASP.NET Core 8 runtime или .NET 8 SDK. Внешняя публикация не выполнялась.

## Ограничения, не скрываемые статусом «проверено»

Docker отсутствует в окружении. Dockerfile, Compose, Caddy/TLS, production cookies и volume подготовлены, но **контейнерный запуск не проверен**. Внешний репозиторий/публичный хостинг не публиковались.

Приёмка относится к локальному приложению одного ресторана. SQLite загружает агрегат целиком и сериализует запись; PRIMARY KEY обеспечивает индексы идентификаторов, но аналитические запросы вычисляются в памяти. Нужна другая стратегия хранения/индексации для большой истории. Снимок ограничивает партии и журналы; полный журнал доступен с пагинацией.

SSE и автосписание проверены с секундным циклом фонового обработчика; API исключает истёкшую партию сразу при запросе. Отдельные роли, несколько ресторанов, отмена заказа, денежные потери без цен не входят в реализованную модель. Прогноз и закупки показывают допущения и отсутствие истории.
