# Решения по усилению

10 октября 2026. Сохраняем один API, SQLite WAL/FULL и транзакции BEGIN IMMEDIATE; расчёты выполняем на копии снимка вне записи. SalesPlanner отдельным модулем, POST /planning для явных параметров, не запускать поиск в SSE. Старый контракт snapshot/ranking сохраняется для совместимости. План не резервирует склад; исполнение через обычный идемпотентный заказ.

Цель без цен: сумма использованных долей исходного пригодного остатка рисковых партий с весом 1 + warningHours/(hoursLeft + 0.25). Вес определён на начало расчёта, возрастает при приближении срока. Единицы не суммируются. Денежный режим выбирает одну валюту и требует цены всех рисковых партий этой задачи. Базовый жадный и поиск оцениваются одинаковой функцией. Равенства: больше полезного расхода по целевой функции, затем меньше порций, затем стабильный порядок ID. На малых задачах полный поиск; при превышении времени/размера допустимое лучшее решение с fallback и честным статусом.

Горизонт 6/12/24 ч либо явно введённый конец смены, часовой пояс ресторана. Предел спроса: явные ручные порции или достаточная история; режим только по складу не заявляет продаваемость. Временные слоты и целые порции; каждая порция проверяется по FEFO в момент приготовления. Кухонная ёмкость задаётся явно.

Цены optional decimal за базовую единицу партии, валюта ISO из списка поддержанных. kg/l делят цену на 1000. Старые записи null. JSON payload позволяет добавить поля без переписывания истории; схема v3 сопровождается предварительной SQLite backup-копией.

## Формальная модель

Для каждой исходно пригодной партии b: q_b — исходный остаток снимка, u_b — запланированный FEFO-расход до expiresAt, h_b — часы до срока на начало расчёта. Риск определяется порогом min(product.warningHours, settings.warningHours). Вес w_b = 1 + settings.warningHours/(h_b + 0.25). Цель risk = Σ w_b*u_b/q_b; money = Σ w_b*u_b*unitCost_b в одной выбранной валюте. Цены всех рисковых партий обязательны для money; без полноты режим отклоняется. В итогах риска выводится ненормированная стоимость и полнота цен, валюты разделены.

Ограничения: каждая порция целая; срок строго позже времени готовности; общая FEFO-потребность всех выбранных блюд не превышает пригодный остаток; суммарные порции блюда <= лимит спроса; суммарные порции слота <= ёмкость кухни. В режиме stock технический предел блюда 10000 соответствует максимальному подтверждаемому количеству в API. При prep=0 все готовятся на start; иначе готовность на start + k*prep, только в открытые часы. Это явно выбранная модель кухни, не оценка реальных длительностей рецептов.

Перебор рассматривает count=cap..0 в стабильном ordinal-порядке ID и слотов. При равной цели выбираются меньшие общие порции; при полном равенстве сохраняется первый вариант. До 64 переменных выполняется DFS с бюджетом 650мс для 20/100, иначе 1500мс и максимум 500000 узлов. Более 64 переменных: ограниченные альтернативные порядки блюд из исходного снимка, не хуже базового. Верхняя граница не вычисляется, gap не заявляется. Время включает базовый расчёт и объяснения; baselineCalculationMs возвращается отдельно. Cache на один последний запрос по revision+параметрам, до 30сек или ближайшего истечения, входа в предупреждение либо изменения окна истории; конкурентные расчёты одного API сериализованы отдельно от writer.

Спрос: окно настроек, уникальные order ID, минимальные дни с наблюдениями и количество заказов. Сглаженные веса weekday/hour нормированы по рабочей неделе; сценарии 0.6/1/1.4. Ручной спрос задаёт ежедневные порции по всему меню, неназванные блюда получают 0. Отказы включаются только при явной гипотезе. Модель прогнозирует потенциальный спрос даже при недоступности блюда, чтобы дефицит не обнулял потребность.

Закупки: совместный непрерывный сценарный расход по продуктам, шаг до 15мин со split по локальному часу/expiry/arrival/явной будущей поставке. Рекомендация = неудовлетворённая потребность после приезда + safetyFactor*спрос после приезда; запас до приезда расходуется один раз. Остатки, истекающие внутри горизонта, перестают удовлетворять будущую потребность. Без достаточной истории/ручного спроса — только операционный дефицит по одной порции каждого активного блюда вместе. Избыток выбранной закупки моделируется FEFO от приезда до её явно заданного срока, максимум 720ч; без спроса или срока результат неизвестен. Ни сценарии, ни интервалы шага не являются статистическими доверительными интервалами.

Спрос/прогноз/закупки разделяют календарь ресторана и сценарную модель. При нехватке истории требуются ручные значения; отклонённые уникальные заказы учитываются только при явном выборе гипотезы. Результаты моделирования обозначаются сценарными, без заявления статистических интервалов.
