# Защита за 5–7 минут

Использовать новый путь FLAGMAN_DB на быстром локальном диске, FLAGMAN_DEMO=true и собственный пароль. `scripts/start.cmd -Demo` или запуск app/Flagman.Api.dll из release-пакета. Загрузить демо один раз: это единый seed с обычной кухней и двумя независимыми сравнениями алгоритмов. Не удалять рабочую БД и не переводить рабочее время. Все числа учебные.

Набор включает цены в RUB, 24 принятых заказа за шесть предыдущих дней, отказы и фактические списания исторических остатков. Исторические операции не расходуют текущие партии. Расчёты по истории доступны сразу. В разделе закупок демо автоматически подставляет срок 48 часов: это позволяет оценить избыток без дополнительных настроек, а черновик получает этот срок и учебные цены. Измените срок для сравнения сценариев. Существующее демо дополняется при запуске или повторном нажатии «Загрузить демо» без удаления введённых данных.

1. **0:00–0:40.** Обзор: доступность активного меню, рисковые партии, Цезарь в стоп-листе. Склад показывает две партии томатов 2 и 3 кг с разными сроками; часть ранней уже использована демо-заказами. Открыть историю и FEFO.
2. **0:40–1:30.** Заказ Капрезе + паста: общий ингредиент суммируется, предпросмотр показывает партии. Подтвердить и сверить журнал. Слишком большой заказ либо Цезарь отвергается целиком; пригодные остатки остальных продуктов сохраняются. Поставка романо возвращает Цезарь в меню.
3. **1:30–2:40.** Горячие предложения: ручные лимиты, 12 ч, приготовление 0, кухня 10000. Остальные блюда оставить 0; «Контрольное A (100 / 10)» и «Контрольное B (100 / 100)» — лимит 10. На складе оба контрольных продукта по 1000 г. План выбирает десять B, расходует обе партии. Таблица риска показывает 100%, остаток 0 и 600 RUB известных закупочных цен. Это сценарная оценка, не реальная экономия.
4. **2:40–3:30.** Для строгого выигрыша отдельный расчёт: контрольные лимиты 0, «Жадный выбор (60 / 60)» и «Улучшенный выбор (50 / 50)» — по 2. Запас редких продуктов по 100 г. Базовый выбирает одну порцию 60/60, улучшенный две 50/50. При срочности w, базовый риск-расход 1.2w, улучшенный 2w. Оба допустимы; оптимум для этой маленькой задачи доказан.
5. **3:30–4:20.** Создать заказ по плану: форма переносит точные блюда/порции. Серверный предпросмотр не меняет склад. Подтвердить, показать FEFO и второй клиент через SSE. Если второй оператор забрал запас, обычное подтверждение даст актуальный отказ без частичного расхода; пересчитать план вручную.
6. **4:20–5:10.** Перевести только демо-время на 24 часа. Истёкшие партии сразу непригодны, monitor списывает каждую один раз, аналитика различает расход и фактические потери. Ещё час не дублирует списание. Неизвестные цены не означают ноль; валюты отдельно.
7. **5:10–6:30.** Закупки: ручной спрос всего меню, например 4 Цезаря за рабочий день, другие 0; доставка 0 ч и срок 24 ч. Расчёт показывает потребность/остаток/избыток. Изменить количество, повторить оценку. Создать черновик, явно задать время поступления и сроки, показать доступность сейчас/к приезду/после; до Сохранить движений нет. Прогноз показывает интервалы и конкретный продукт, а отсутствие достаточной истории — явную метку.
8. **6:30–7:00.** Открыть HACKATHON_VERIFICATION: domain/oracle/E2E/backup/нагрузка и ограничения. Публичные ссылки показывать только после реальной публикации/проверки; пока доступен локальный release-пакет. GitHub remote существует, новые изменения/CI и внешнее HTTPS не подтверждены.

## Ответы на вопросы

- Почему порции рейтинга не складываются? Каждое блюдо отдельно может претендовать на один и тот же ингредиент; совместный план моделирует общий расход.
- Что при двух заказах? Очередь одного API и BEGIN IMMEDIATE для конкурирующих процессов; нехватка отклоняет весь заказ.
- Повтор после потери ответа? Payload и Idempotency-Key сохранены вместе; повтор возвращает один прежний результат. Другой payload требует нового ключа после завершения старого намерения.
- Почему приоритет повышается? Вес 1 + warningHours/(hoursLeft + 0.25) растёт при приближении срока; используются доли исходных партий, не сумма граммов и миллилитров.
- Где точность? ProvenOptimal только после полного перебора. При бюджете времени/узлов или большой задаче — допустимый bounded-search и базовый fallback; gap без верхней границы не заявлен.
- Откуда спрос? Достаточная история с календарным профилем либо явный ручной ввод; stock оценивает только склад. Отказы включаются лишь по настраиваемой гипотезе.
- Как проверен прогноз? 14 синтетических held-out окон, все будущие события исключены из обучения, неудачные случаи сохранены. Реальные данные ресторана пока отсутствуют.
- Что значит предотвращение потерь? Потенциальный расход по сценарию плана; фактические потери считаются по движениям expiry и исторической цене.
- Как восстановить? SQLite backup API, integrity и exact reconciliation, restore в новый путь, согласованная пара приложения/БД, новые ключи и отзыв сессий; RUNBOOK.
- Почему диск важен? FULL commit обеспечивает сохранность, но его задержка на D: нарушала цель. На C: тот же профиль прошёл; целевой хост/volume нужно измерить отдельно.

## Повторимость сравнения

`tests/HackathonChecks.cs` использует фиксированные случаи и Random(42), публикует все 65 сравнений в planner-comparison.json. planner-benchmark.json содержит все пять замеров каждого масштаба. `scripts/verify-release.ps1` создаёт новые БД/порты. Генератор seed=42 имеет стабильный LCG и идемпотентные ключи; повтор seed не повторяет расход. Для нового независимого демо использовать новый файл БД.
