Схема v2 и архивы 1.1.0-rc1 требуют совместимого приложения; откат выполняется с согласованной копией базы. Подробности и ограничения — в RUNBOOK.

Дизайн: светлая навигация по рабочим задачам, зелёный акцент, простые формы и адаптивная вёрстка. Правила UX/UI Agent Skills и результаты проверок описаны в docs/DESIGN_APPLICATION.md.

## Локальный запуск (Windows / PowerShell)

Требуются Node.js 22+ и .NET 8 SDK. В этом workspace SDK уже установлен в `.tools/dotnet` и автоматически используется скриптом.

```powershell
cd D:\Progs\hack
$env:FLAGMAN_PASSWORD = 'your-private-password-at-least-10-characters'
.\scripts\start.cmd -Demo
```

Откройте http://127.0.0.1:5080 и введите заданный пароль. Нажмите **Загрузить демо**. По умолчанию скрипт использует `backend/data/demo/flagman.db` для демо и `backend/data/production/flagman.db` без `-Demo`; повторный запуск сохраняет склад. Старую `backend/data/flagman.db` скрипт не меняет. FLAGMAN_DB явно выбирает иной путь. Скрипт собирает frontend и запускает ASP.NET Core, который отдаёт интерфейс и API с одного адреса. Без `-Demo` генератор и изменение времени недоступны; база с сохранённым демо-сдвигом не принимается.

`start.cmd` запускает PowerShell с `ExecutionPolicy Bypass` только для дочернего процесса; системная политика не меняется. Если `.ps1` блокируется сообщением «выполнение сценариев отключено», используйте этот вариант. Эквивалент: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -Demo`. Вместо примера пароля задайте собственный.

Для новой демонстрации задайте путь к новой БД перед запуском, не удаляя текущую:

```powershell
$env:FLAGMAN_DB = 'D:\Progs\hack\backend\data\demo-2.db'
.\scripts\start.cmd -Demo
```

Linux/macOS: `npm ci && npm run build` в `frontend`, затем `FLAGMAN_PASSWORD='...' FLAGMAN_DEMO=true ASPNETCORE_ENVIRONMENT=Development dotnet run --project backend/Flagman.Api.csproj --urls http://127.0.0.1:5080` из корня.

## Проверки

```powershell
./scripts/test.ps1
```

Доменные и интеграционные тесты используют реальный временный SQLite и управляемое время. Проверяют FEFO, общий ингредиент, конкуренцию соединений, повторы/конфликты, откат, повторный запуск, истечение, рекомендации, закупки, прогноз и воспроизводимость генератора. Test runner — обычный C# executable с assertions; ненулевой exit означает ошибку.

E2E: запустите сервер на 5080 с **новой пустой демо-базой** и тем же паролем в окружении теста. Тест намеренно создаёт данные и переводит демо-время.

```powershell
cd frontend
$env:PLAYWRIGHT_BROWSERS_PATH = 'D:\Progs\hack\.tools\browsers'
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

В стандартной установке вне этого workspace можно не задавать PLAYWRIGHT_BROWSERS_PATH. Снимки desktop/mobile и ошибки тестов появляются в `test-results`. Детали приёмки: `TASKS.md`, `docs/VERIFICATION.md`.

## Развёртывание

Скопируйте `.env.example` в `.env`, задайте собственный пароль; `docker compose up --build -d`. Интерфейс: https://localhost:8443. Caddy использует внутренний сертификат: установите корневой сертификат Caddy в доверенное локальное хранилище для полноценной проверки HTTPS. Для публичного домена замените адрес Caddy, уберите `tls internal` и привяжите 443 к внешнему интерфейсу; настройте DNS, TLS и резервное копирование.

`GET /api/live` — liveness; `/api/ready` и `/api/health` — дешёвая проверка соединения и схемы v2. Volume `/data` содержит БД и ключи сессии: доступ к нему должен иметь только процесс приложения/администратор, ключи нельзя публиковать. Инструмент Maintenance и скрипты backup/restore используют SQLite backup API и сверку движений; копирование только `.db` при активном WAL ненадёжно.

Пакет подготовлен к публикации. Docker и внешний хостинг требуют отдельной проверки в доступной среде; публичная ссылка и репозиторий не создавались.

## Правила и ограничения

- Граммы, миллилитры и штуки не суммируются. Ввод kg/l конвертируется в g/ml; точные decimal до трёх знаков после запятой.
- При `now >= expiresAt` партия непригодна сразу. Фоновое списание и обновление SSE идут с секундным интервалом; срочность рекомендаций дополнительно обновляется раз в минуту. UTC хранится в БД, часовой пояс интерфейса настраивается.
- Формы даты/времени используют часовой пояс ресторана независимо от пояса компьютера. Время в разрыве/повторе DST отклоняется как неоднозначное. Поле даты без времени и API `expiryDate` задают границу начала следующего дня в поясе ресторана.
- Повтор принятого или отклонённого заказа возвращает сохранённый результат; новый состав с тем же ключом даёт 409. Рецептуры проданных блюд неизменяемы; создайте новую версию блюда.
- Рейтинг рекомендаций и совместный план различаются. Общий виртуальный склад предотвращает двойной расход. Лимит 100 порций на блюдо ограничивает объём расчёта.
- Прогноз — модель равномерного спроса. Ожидаемый момент означает границу остатка для одной порции; точность продаж не гарантируется. Без истории показывается её отсутствие; истечение всё равно учитывается. Закупки без истории восстанавливают возможность отдельной одной порции, не обещая совместную доступность всего меню.
- Снимок ограничен 500 партиями (активные сначала) и 100 записями журналов; полный журнал имеет SQL-пагинацию, поиск и устойчивый порядок. Поиск партий охватывает весь склад. Dashboard читает пригодный склад и нужное окно истории, SSE и Monitor используют отдельные выборки, заказ выбирает достаточный запас нужных ингредиентов по FEFO. Полное чтение сохранено для контрольной сверки и демонстрационного генератора; PostgreSQL не вводится без измерений.
- Авторизация управляющего — одна роль для локального ресторана. Раздельные роли и несколько ресторанов не реализованы. Генератор по умолчанию выключен; повтор seed не применяет ранее созданные события повторно.

API: `docs/API.md`. Технические решения: `docs/DECISIONS.md`. Сценарий защиты: `docs/DEMO.md`.

## Готовая Release-сборка

Историческая сборка MVP сохранена в `output/flagman-app.zip` и `output/app`; её не использовать с новой схемой v2. Новые кандидаты `output/flagman-1.1.0-rc1-*.zip` создаются `scripts/package-release.ps1 -Evidence <успешная папка release-проверки>`; рядом записывается SHA256. Нужен ASP.NET Core 8 runtime или .NET 8 SDK. Из распакованной папки `app` задайте FLAGMAN_PASSWORD, для локального HTTP также ASPNETCORE_ENVIRONMENT=Development, затем `dotnet Flagman.Api.dll --urls http://127.0.0.1:5080`. При использовании локального SDK из корня проекта путь к dotnet: `D:\Progs\hack\.tools\dotnet\dotnet.exe`. Production оставляет Secure cookies и требует HTTPS. Секреты, рабочие БД и ключи в новый архив не включаются.
