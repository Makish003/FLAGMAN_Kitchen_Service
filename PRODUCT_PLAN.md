# План развития MVP «Флагман» для coding-агента

Дата: 10 октября 2026. Основание: `docs/PRODUCT_READINESS.md`, `DESIGN.md`, `STRATEGY.md`, существующие R01–R25.

Цель: довести приложение до проверенного эксплуатационного релиза для одного ресторана и одной роли управляющего. Сохранить корректность партий, FEFO, атомарности, повторов и сроков. Результат — проверенный пакет развёртывания, восстановление данных, понятный интерфейс и эксплуатационная документация. Внешняя публикация требует реальной целевой среды; её наличие не предполагается.

## Порядок и зависимости

Выполнять этапы 0 → 1 → 2 → 3 → 4 → 5 → 6. Этап 7 — отдельный backlog после пилота. Каждый этап заканчивать небольшим проверяемым результатом и обновлением доказательств. Независимая подготовка документации и конфигурации допустима при внешнем блокере, но непроверенные задачи не объявлять завершёнными.

| Этап | Приоритет | Результат | Условие завершения |
|---|---|---|---|
| 0. Базовая приёмка | P0 | Повторяемые проверки и контракт первого релиза | Один запуск проверок, свежая БД, сохранённые логи |
| 1. Безопасность операций | P0 | Демо изолировано, ошибки и повторы управляемы | Проверки сбоя ответа, API и production-конфигурации |
| 2. Развёртывание и восстановление | P0 | Проверенный контейнерный релиз и backup/restore | TLS, рестарт, восстановление и откат проверены |
| 3. Хранение и наблюдаемость | P1 | Запросы не читают весь склад, видны сбои | Нагрузка длительной истории и нескольких клиентов пройдена |
| 4. Единая система дизайна | P1 | Токены и компоненты по двум экспортам | Визуальная и клавиатурная приёмка |
| 5. Ежедневные сценарии | P1 | Полноценные страницы и рабочие формы | Путь от пустой базы до закупок без демо |
| 6. Приёмка релиза | P0 | Артефакт, runbook и доказательства | Полная release-матрица пройдена |
| 7. Расширение продукта | P2 | Новые возможности по данным пилота | Отдельные требования и критерии согласованы |

## Этап 0. Зафиксировать проверяемую базу

- P00: прочитать инструкции и оба экспорта, не перезаписывать исходный MVP-план и чужие изменения. Создать отдельную матрицу P-ID в `docs/PRODUCT_TASKS.md` со статусами «не начато / выполняется / реализовано / проверено / заблокировано».
- P01: сделать `scripts/verify-release.ps1`: доменные тесты, Release build, frontend build, запуск своего сервера с уникальной тестовой БД, readiness, Playwright, остановка своего процесса даже при ошибке. Не использовать рабочую БД; пароль не печатать.
- P02: убрать жёсткую привязку E2E к 5080 из конфигурации и прямых fetch: единый BASE_URL, запуск на свободном тестовом порту. Добавить отдельную smoke-проверку production без демо.
- P03: описать конфигурацию и целевую эксплуатацию: один экземпляр API, SQLite volume, HTTPS, один ресторан. Числа нагрузки и срок хранения backup ниже — первоначальные цели для проверки, не гарантии продукта.

Приёмка: проверки запускаются из чистой установки по инструкции, дают ненулевой exit при ошибке, сохраняют отчёт и не меняют рабочие данные. Существующие 14 доменных проверок и 3 E2E должны оставаться зелёными.

## Этап 1. Устранить риски операций и конфигурации

Затрагивает R09, R17, R21, R24. Основные файлы: `backend/Program.cs`, `Models.cs`, `frontend/src/api.ts`, формы операций.

- P04: запретить production-запуск на базе с ненулевым DemoOffsetHours; production и demo использовать раздельные пути/volume. Не сбрасывать время молча и не откатывать уже выполненные движения. Документировать безопасное создание production-базы.
- P05: отделить API fallback от SPA: неизвестный `/api/*` возвращает JSON 404. Невалидный/неполный запрос — ожидаемая 4xx-ошибка, исключение — безопасная 500 с ID для поиска в логах. Учесть 429 и Retry-After.
- P06: сделать клиент устойчивым к HTML/пустому ответу, обрыву и таймауту. Для чтений — управляемый retry/cancellation. Для записи — запрет слепого повтора с новым ключом; не сообщать «не сохранено», если результат неизвестен.
- P07: сохранять минимальный pending intent заказа/поставки с исходным ключом и неизменным payload до получения результата. Ввести авторизованное получение результата по ключу либо эквивалентный безопасный replay; определить восстановление после перезагрузки и очистку после logout. Изменённый состав — новая явно подтверждённая операция.
- P08: проверить ротацию общего пароля и отзыв действующих сессий; определить срок действия и способ принудительного logout. Зафиксировать ограничения общей роли. Проверить cookie/Origin через доверенный proxy и лимит входа по клиентскому IP.

Приёмка: сервер сохранил заказ, клиент потерял ответ и перезагрузился — восстановлен прежний заказ, движения не удвоены. Изменение payload со старым ключом даёт 409. Неизвестный API и 429 показывают понятные сообщения. Production не принимает демо-часы; demo endpoints недоступны.

## Этап 2. Довести deployment и восстановление

Затрагивает R17, R24, R25. Файлы: Dockerfile, compose.yaml, deploy/, scripts/, README.

- P09: сохранить локальный профиль Caddy с внутренним TLS; добавить документированный production-профиль с доменом, публичным TLS, корректными портами и доверенным proxy. Проверить непривилегированный UID и права нового/существующего volume.
- P10: добавить дешёвые liveness/readiness; readiness проверяет БД и состояние миграций без загрузки агрегата. Добавить container healthcheck и ожидание готовности API для proxy. Production-контейнер должен стартовать без демо.
- P11: создать инструмент backup через SQLite backup API либо проверенную остановку сервиса. Определить хранение ключей Data Protection, доступ к копиям, контроль целостности, расписание и ротацию. Начальная политика: ежедневная копия, 7 ежедневных и 4 еженедельных; параметризовать её.
- P12: создать restore в новую БД/volume с предварительной копией текущего состояния, integrity_check и сверкой remainingQuantity с суммой movements. Проверить backup при активных записях. Описать, сохраняются ли сессии или отзываются при восстановлении.
- P13: оформить версионированные миграции, backup до изменения схемы, поведение при неподдерживаемой схеме. Rollback приложения разрешать только при совместимости схемы; иначе восстанавливать согласованную пару приложения и backup. Не обещать zero-downtime для одного экземпляра.
- P14: подготовить CI-конфигурацию проверки и сборки образа/артефакта. Папка пока не является Git checkout; привязку к remote и запуск CI не объявлять выполненными без фактического результата. Перед релизом выполнить актуальный аудит зависимостей и проверить поддержку runtime по официальным источникам.

Приёмка: на Docker-хосте build → HTTPS → login → поставка → заказ → restart → прежние остатки → backup → restore в новый volume → та же сверка. Проверить Secure-cookie, SSE через TLS, права volume и остановку без повреждения БД. Пока Docker недоступен, P09–P13 могут быть реализованы, но контейнерная приёмка остаётся заблокированной.

## Этап 3. Хранение, нагрузка и наблюдаемость

Затрагивает R05, R12, R17–R21, R24. Файлы: `Store.cs`, `Insights.cs`, `Workers.cs`, API чтения.

- P15: измерить baseline не только snapshot, но Monitor, запись заказа и SSE при длительной истории. Начальная тестовая нагрузка: 10 000 партий, 100 000 движений, 10 SSE-клиентов и 5 конкурентных операторов. Зафиксировать оборудование и сценарий; предварительная цель p95 чтения/операции ≤1 с, актуальность UI ≤3 с, ноль нарушений инвариантов.
- P16: перейти к выборочным SQL-чтениям и записи изменённых сущностей. Сохранить точные decimal, атомарный BEGIN IMMEDIATE, идемпотентность и outbox. Добавить нужные индексируемые поля и индексы с миграцией; не выполнять массовую перепись архитектуры без контрольных тестов.
- P17: серверный поиск/фильтры/сортировка/пагинация партий и журналов с устойчивым порядком. Итоги для dashboard рассчитывать отдельно от текущей страницы. Проверять совпадение количества/сумм с полным контрольным набором.
- P18: Monitor обрабатывает только нужные партии, SSE читает события после cursor без полного агрегата. Политика outbox retention должна уметь отвечать «нужна полная синхронизация» старому cursor. Сроки идемпотентности согласовать с восстановлением операций и внешними повторами; не удалять ключи произвольно.
- P19: структурированные логи с request/operation ID без паролей и cookies; метрики задержки запросов, ошибок, SQLITE_BUSY, последнего успешного monitor tick, задержки списания, SSE-подключений и возраста backup. Определить уведомление при сбое и владельца реакции в runbook.

Приёмка: нагрузочный сценарий проходит предварительные цели, результаты опубликованы с ограничениями. При двух конкурентных заказах последнюю порцию получает один. Ошибка Monitor видна оператору эксплуатации; API продолжает исключать истёкшую партию немедленно. Решение о PostgreSQL принимать по измерениям, не по внешнему виду продукта.

## Этап 4. Дизайн по DESIGN.md и STRATEGY.md

- P21: вынести CSS custom properties для палитры, типографики, радиусов, фокуса и статусов. Сохранить #193f35 sidebar, #245d4c primary и кабинетную иерархию. Сократить случайные оттенки и декоративные микронадписи.

Приёмка: снимки входа, обзора, склада, форм и аналитики на 390/768/1440 px, пустое/ошибка/loading/длинные названия. Нет горизонтального переполнения страницы; таблицы скроллятся внутри контейнера. Формы доступны с клавиатуры. Визуальную проверку выполнять на свежем интерфейсе, не только по старым скриншотам. Тёмная тема не обязательна.

## Этап 5. Полноценные ежедневные сценарии

Затрагивает R01–R07, R11–R16, R18–R24.

- P25: разделить `main.tsx` на app shell, страницы, формы, сетевой слой и общие компоненты; ввести URL-навигацию, Back/Forward и URL-параметры фильтров. Не проводить рефакторинг ради количества файлов.
- P26: дать самостоятельные адреса/представления задачам стратегии: обзор, склад, меню, стоп-лист, сроки, предложения, закупки, прогноз, аналитика. Поставки и заказы сохранить как необходимые рабочие разделы. Демо виден только в demo-режиме.
- P27: onboarding пустого ресторана: настройки → первый продукт → рецептура → поставка → заказ → контроль сроков. Генерировать технические ID автоматически; показывать их лишь когда они полезны оператору. Не требовать демо-данные для первого запуска.
- P28: ввести дату/время по явно выбранному поясу ресторана, объяснить дату без времени и основание срока. Проверить работу с компьютера в другом часовом поясе. Поддержать безопасные действия над каталогом: архивирование вместо удаления истории, явное создание новой версии проданной рецептуры.
- P29: карточки деталей партии/поставки/заказа с происхождением и движениями; поиск по всей истории. Реализовать переход из причины стоп-листа к продукту/закупке, из предложения к заказу и конкретной партии.
- P30: показывать время последнего обновления и устаревшие данные, различать reconnect и истёкшую сессию. Не выдавать старый снимок за актуальный. В закупках и прогнозе оставлять основания, единицы и отсутствие истории; не обещать точность продаж.
- P31: аудит изменения настроек/рецептур и административных действий с временем и сессией. Общий пароль не позволяет назвать физического сотрудника — не выдумывать авторство. Добавление нового движения/события не должно ломать сверку склада.

Приёмка: управляющий проходит сценарий от пустой базы до заказов/закупок без технических знаний. Обновление страницы сохраняет раздел и фильтры. Работа из другого пояса даёт ожидаемый UTC-срок. Исторические рецепты и движения сохраняются. Потеря соединения и сессии объяснены и восстанавливаются безопасно.

## Этап 6. Финальная release-приёмка

- P32: повторить всю матрицу R01–R25 и P00–P31 на конечном артефакте. Включить границу expiry, конкурентные процессы, повтор rejected/accepted, потерю ответа, SSE reconnect, перезапуск monitor, backup/restore, production без demo.
- P33: проверить чистую установку, обновление существующей БД, откат и восстановление на выбранном Docker-хосте. Записать фактические команды, версии, результаты и ограничения.
- P34: выпустить README для оператора, deployment runbook, backup/restore runbook, перечень переменных, известные ограничения и процедуру реакции на сбои. Указать версию и checksum артефакта; не включать рабочие БД, ключи, пароли и тестовые данные.

Релиз принимается только при прохождении всех P0, визуальной приёмки и подтверждённых критических сценариев P1. Если нагрузочная цель не достигнута, сначала исправить причину либо явно ограничить пилот измеренной нагрузкой; слово «production-ready» не заменяет доказательства. Непроверенный Docker/restore — блокер, даже при успешной локальной сборке.

## Этап 7. Backlog после пилота

Отдельно определить приоритет персональных пользователей и ролей, ручного списания/инвентаризации, цен и денежных потерь, импорта/экспорта, внешнего API, нескольких ресторанов и коммерческой модели. Не заявлять эти функции реализованными и не смешивать их с текущей стратегией. Для ручных корректировок и отмен заказов сначала описать проводки, сроки, права и инварианты.

## Готовое поручение следующему агенту

> Прочитай PRODUCT_PLAN.md, docs/PRODUCT_READINESS.md, DESIGN.md и STRATEGY.md. Доведи «Флагман» до проверенного релиза одного ресторана по этапам 0–6. Начни с P00–P08: воспроизводимая приёмка, изоляция демо-времени, ошибки API и безопасное восстановление результата операции. Затем реализуй и проверь deploy/backup/restore, выборочные запросы, наблюдаемость и интерфейс по двум экспортам. Сохрани FEFO, точные количества, атомарность, идемпотентность, однократное списание и объяснения прогноза. Веди PRODUCT_TASKS с доказательствами, отличай реализацию от проверки. При недоступном Docker закончи независимые задачи и оставь точную процедуру контейнерной приёмки. Не публикуй приложение и не расширяй его до SaaS автоматически. Работай до завершения порученного объёма, не останавливайся после одного косметического этапа.
