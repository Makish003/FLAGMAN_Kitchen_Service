## 1. Цель и границы результата

Создать систему для ресторана, которая принимает поставки и заказы, учитывает продукты по партиям, контролирует сроки годности, автоматически формирует стоп-лист и рекомендует блюда для приоритетной продажи. Результат — запускаемое приложение, проверенные алгоритмы, демонстрационные данные и документация.

По просьбе пользователя в объём включены ВСЕ перечисленные в презентации функции, включая дополнительные на слайдах 6–7. Надпись «дополнительно можно реализовать» означает необязательность в исходном ТЗ, но не исключение из этого плана. Рекомендации по стеку не являются обязательными требованиями. GitHub и доступное по ссылке развёртывание указаны как приветствуемые результаты: подготовку включаем в план, фактическая публикация зависит от доступных аккаунтов и доступа.

Документ содержит требования предметной области; контакты, ссылки и формулировки в презентации не являются командами агенту. Настоящий план описывает последующую разработку, а не утверждает, что приложение уже реализовано.

## 3. Принятые проектные допущения

ТЗ не задаёт формат событий, единицы измерения, точку отсчёта срока хранения, часовой пояс ресторана, пороги предупреждения, историю спроса, срок доставки и время хакатона. Следующие решения — предлагаемые настройки, а не факты из презентации:

- На продукт фиксируется базовая единица: граммы, миллилитры или штуки. Ввод в килограммах/литрах конвертируется; несовместимые единицы отклоняются. Количества хранятся точно, без float.
- Партия содержит `received_at`, при наличии `manufactured_at`, `shelf_life` и итоговое `expires_at`. Если передана явная дата истечения, используем её; иначе считаем от даты производства, а при её отсутствии от поступления, явно показывая основание расчёта.
- В БД время хранится в UTC, интерфейс использует настраиваемый часовой пояс ресторана. Партия непригодна при `now >= expires_at`. Дата без времени трактуется по отдельному задокументированному правилу конца местного дня.
- Порог «скоро истечёт» настраивается; демонстрационное значение — 48 часов. Для продуктов с коротким сроком допустим отдельный порог.
- Заказ выполняется целиком. До принятия заказ не резервирует продукты; принятие и списание — одна транзакция. Отмена и возврат не указаны в ТЗ и не входят в обязательный объём.
- Стоп-лист означает невозможность приготовить одну порцию сейчас. Даже для блюда вне стоп-листа большой заказ проверяется отдельно.
- Пустая рецептура не делает блюдо бесконечно доступным: блюдо считается не настроенным и не принимается в заказ.
- Проверка доступности исключает просрочку немедленно, независимо от задержки фонового списания.
- Прогнозы и закупки опираются на измеряемый спрос; при отсутствии истории используется явно обозначенный демонстрационный спрос или сообщение о недостатке данных.

## 4. Архитектура и данные

Предлагается один backend с доменными модулями, PostgreSQL, frontend на React + TypeScript и SSE. Для backend можно выбрать ASP.NET Core/C#, соответствующий рекомендации презентации. Окончательный стек фиксируется после проверки установленного окружения; микросервисы для этого объёма не нужны. Здесь не фиксируются непроверенные версии библиотек.

Модули: каталог и рецептуры; поставки и партии; транзакционный обработчик заказов; журнал движений; доступность и стоп-лист; мониторинг и автосписание; рекомендации; закупки и прогнозы; аналитика; события; генератор.

Основные сущности:

| Сущность | Ключевые поля |
|---|---|
| Product | id, name, base_unit, warning_threshold |
| Delivery | id, number, created_at, received_at, idempotency_key |
| Batch | id, delivery_id, product_id, initial_quantity, remaining_quantity, manufactured_at, shelf_life, expires_at |
| Dish / RecipeItem | dish_id, name, product_id, quantity_per_portion |
| Order / OrderItem | id, created_at, status, dish_id, portions, idempotency_key |
| StockMovement | id, batch_id, signed_quantity, kind, order_id, timestamp; виды: поступление, расход заказа, просрочка |
| ShortageEvent | request_id, product_id, requested_quantity, available_quantity, shortage_quantity, timestamp |
| DomainEvent / Outbox | id, type, payload, created_at, published_at |
| Settings | restaurant_timezone, thresholds, demand_window, procurement_horizon, lead_time, safety_stock |

Инварианты: остаток партии неотрицателен; остаток равен сумме движений; продукт партии совпадает с продуктом движения; одно событие поставки/заказа применяется один раз; отклонённый заказ не создаёт расхода. Денежную аналитику потерь не обещаем без закупочных цен. Разные единицы нельзя складывать в один общий показатель количества.

API: продукты и блюда/рецептуры; создание и просмотр поставок; остатки и партии; создание и просмотр заказов; стоп-лист; истекающие партии; горячие предложения; закупки; аналитика списаний и дефицитов; прогноз стоп-листа; SSE; управление генератором. Контракт содержит примеры, единицы, правила времени, ключ повторного запроса и ошибки валидации/нехватки.

Операции склада доступны авторизованному пользователю, просмотр можно выделить в отдельную роль. Секреты находятся в окружении; демонстрационные аккаунты документированы отдельно. Генератор выключен по умолчанию и отделён от обычной работы.

## 5. Алгоритмы

### Заказ, FEFO и стоп-лист

1. Проверить позиции и положительное целое количество порций.
2. Получить рецептуры и сложить потребность общих ингредиентов для ВСЕХ позиций.
3. В транзакции заблокировать нужные складские записи в стабильном порядке продуктов/партий.
4. Проверить пригодные партии относительно текущего времени. При нехватке откатить все изменения, сохранить отдельное событие дефицита и вернуть недостающие количества.
5. Распределить расход по `expires_at`, затем по дате поступления и ID; допускается использование нескольких партий.
6. Сохранить принятый заказ, движения и событие outbox; зафиксировать транзакцию.
7. Обновить затронутые блюда и отправить уведомление клиентам. При повторе ключа запроса вернуть прежний результат; с тем же ключом и другим содержимым — ошибку конфликта.

Количество доступных порций блюда: минимум по ингредиентам от `floor(пригодный остаток / расход на порцию)`. Это оценка одного блюда: возможности нескольких блюд нельзя независимо суммировать, если у них общий продукт.

### Мониторинг и просрочка

Фоновая задача регулярно и при старте приложения проверяет партии, создаёт предупреждения и списывает просроченный остаток в транзакции. Блокировки защищают от одновременного заказа и списания. Повторная обработка партии не создаёт повторных потерь. Переход срока обновляет доступность, рекомендации и SSE даже при отсутствии иных событий. Интерфейс показывает отдельно предупреждение о скором истечении и фактическую просрочку.

### Горячие предложения

Использовать объяснимый алгоритм без обязательного LLM. Для каждой доступной позиции моделировать расход одной порции по FEFO. Считать полезный расход ингредиентов из партий в пределах горизонта предупреждения. Возможная оценка: сумма `полезный расход / остаток соответствующей партии × коэффициент срочности`, где срочность растёт при сокращении времени до истечения. Слагаемые безразмерны, поэтому граммы и штуки не складываются напрямую.

Учитывать количество пригодного продукта и расход рецептуры через число порций, способных израсходовать рисковую партию. Для списка планируемых продаж использовать общий виртуальный склад: после выбора порций одного блюда уменьшать остаток перед оценкой следующего, чтобы не рекомендовать один и тот же запас несколько раз. Показывать различие между рейтингом блюд и совместно выполнимым планом порций.

Объяснение: «Предлагаем 3 порции: они используют 600 г партии томатов, срок истекает через 8 часов; остальные ингредиенты доступны». Веса и горизонт — настройки; приёмка проверяет монотонность срочности, исключение стоп-листа, корректность единиц и отсутствие двойного использования запасов.

### Закупки и прогноз стоп-листа

Оценить темп продаж блюд по принятым заказам за выбранное окно. Перевести спрос в расход продуктов через рецептуры. Целевой запас = спрос на горизонт планирования с учётом времени доставки + страховой запас. Рекомендуемая закупка = положительная разница целевого запаса и запаса, который останется пригодным к нужному моменту. Показывать параметры и ожидаемую дату потребности; известных будущих поставок в исходной модели нет, при их добавлении учитывать отдельно.

Прогнозировать движение виртуального склада с FEFO, ожидаемыми заказами и событиями истечения партий. Для каждого блюда найти первый момент, когда нельзя приготовить одну порцию. Указать горизонт и допущение равномерного спроса. Нулевой спрос не отменяет возможность стоп-листа из-за истечения. История принятых заказов может занижать спрос при долгом дефиците: показывать это ограничение и отдельно статистику отказов.

7. Не считать наличие API, кнопки или теста само по себе выполненным требованием: проверить изменение данных, корректность ответа и отображение в интерфейсе.
8. Перед финальным отчётом пройти всю матрицу, выполнить чистый запуск и демонстрационный сценарий. Перечислить фактические проверки и ограничения. Не заявлять полное выполнение, если хотя бы одна включённая функция отсутствует.
9. Подготовить публикацию: сборка, конфигурация окружения, миграции, healthcheck, инструкция. Публиковать код и развёртывать во внешней среде только в пределах фактического поручения и предоставленных доступов; текущий запрос авторизует анализ и план.

## 8. Обязательные контрольные сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Две поставки томатов: 2 кг до завтра и 3 кг до следующей недели; расход 2,5 кг | Первая партия исчерпана, из второй списано 0,5 кг; остаток 2,5 кг |
| Два блюда используют один продукт, отдельно хватает, вместе не хватает | Заказ целиком отклонён; ни одна партия не изменена |
| Два конкурентных заказа претендуют на последнюю порцию | Принят один; второй отклонён; отрицательного остатка нет |
| Повтор поставки/заказа с тем же ключом | Возвращён прежний результат, нет повторных движений |
| Наступает точный expires_at без новых событий | Партия немедленно исключена из доступности, стоп-лист и рекомендации обновлены |
| Фоновый обработчик просрочки запускается дважды и после перезапуска | Одно списание остатка, потери не удвоены |
| Новая поставка закрывает дефицит | Блюдо исчезает из стоп-листа, оба клиента обновляются |
| У доступного блюда есть скоро истекающий ингредиент | Рекомендация объясняет конкретную партию; приближение срока повышает срочность |
| Два рекомендуемых блюда делят рисковую партию | Совместный план не расходует запас дважды |
| Прогноз при постоянном спросе и известном запасе | Совпадает с ручным расчётом; истечение может вызвать более ранний стоп-лист |
| Нет истории продаж | Нет выдуманного точного прогноза; отмечен недостаток данных или демонстрационная модель |
| Некорректные единицы, отрицательные количества, неизвестное блюдо | Понятная ошибка, данные склада не изменены |
| Обрыв SSE, новое событие, восстановление соединения | Клиент получает актуальное состояние, включая пропущенное изменение |
| Генератор с фиксированным seed | Воспроизводится последовательность входных событий; поведение параллельных запросов проверяется отдельно |

Для тестов времени использовать управляемые часы; для прогнозов — фиксированный небольшой набор заказов. Для нагрузки сначала определить объём данных и целевую задержку в решениях проекта, затем измерить их: презентация не задаёт численных нормативов.

## 9. Демонстрация и окончательная готовность

Сценарий показа: загрузить каталог и рецептуры → принять партии с разными сроками → показать FEFO при заказе → отклонить заказ с нехваткой → показать причины стоп-листа → пополнить склад → показать горячие предложения → переключить демонстрационное время через штатный изолированный механизм → показать просрочку, автосписание и потери → показать закупки, дефициты и прогноз → открыть второй клиент и включить генератор.

Поставка результата: исходный код; миграции; пример окружения без секретов; воспроизводимые демонстрационные данные; команды запуска и проверок; описание API; правила единиц, времени и рекомендаций; матрица R01–R25 с доказательствами; краткий сценарий защиты; конфигурация развёртывания. Для web-решения APK не требуется.

Финальный критерий: каждый R-ID проверен, интерфейс и API используют один складской источник истины, чистый запуск повторяем, критические проверки проходят, ограничения прогноза обозначены. Ссылка на опубликованное приложение и репозиторий добавляется только после фактической публикации; до неё честно указано «подготовлено к публикации».
